# Options Data Service

Self-hosted service that streams options market data (quotes, mark price,
Greeks) from TastyTrade via DXLink, stores it in TimescaleDB, and exposes a
query API for backtesting — see `PLAN.md` for the full project plan and
rationale.

**Status: the full pipeline (Tasks 1-9) is built, tested, and running.**
Auth, contract resolution/refresh, live bar aggregation, historical
backfill, Black-Scholes Greeks reconciliation, continuous aggregates, and
the query API are all real (not placeholders). Task 10 (this update) is
deployment polish: Docker healthchecks/resource-limit guidance and this
README. Only Task 11 (monitoring/alerting) remains, and it's explicitly
lowest-priority/optional in `PLAN.md` — the pipeline runs unattended fine
without it, just with less visibility than a dedicated alert would give
you if it silently stopped.

## Setup

### 0. Get TastyTrade OAuth2 credentials

Username/password auth was discontinued by TastyTrade on Dec 1, 2025 —
OAuth2 (`client_secret` + `refresh_token`) is the only supported method
now. Full walkthrough: `scripts/task0_spike/README.md`. Short version:

1. Create an OAuth application on TastyTrade's OAuth Applications page
   (check the market-data scopes you need).
2. Generate a refresh token — easiest via **OAuth Applications > Manage >
   Create Grant** on the TastyTrade website, or run
   `python scripts/task0_spike/get_refresh_token.py` (add `--sandbox` for
   a cert account) for a guided browser flow.
3. Keep the `client_secret` and `refresh_token` handy for step 2 below —
   `client_id` itself isn't needed at runtime, only during this one-time
   setup.

### 1. Configure and start the stack

```bash
cp .env.example .env      # fill in POSTGRES_PASSWORD and the two TastyTrade values from step 0
cp config.example.yaml config.yaml   # adjust tickers/deltas as desired — see "Configuring tickers" below
docker compose up --build
```

This will:
1. Start TimescaleDB and wait for it to report healthy.
2. Run `alembic upgrade head` once (the `migrate` service) to create the schema.
3. Start `ingestion` (streams live data) and `api` (serves queries) containers.

**Heads up on step 2, first run only:** two of the migrations
(`0002_continuous_aggregates.py`, `0003_underlying_continuous_aggregates.py` — the
5m/15m/30m/1h/1d/1w continuous aggregates) were built without access to a real TimescaleDB instance to
test against, unlike every other migration in this repo. They're carefully reasoned (see each file's own
docstring for the window-sizing/compression-timing rationale) but higher-risk. If `migrate` fails on one
of these, check `docker compose logs migrate` — it's more likely to need a small fix than the rest of
the schema is.

### 2. Verify data is flowing

```bash
# Containers up and healthy?
docker compose ps
# `api` and `timescaledb` should show "healthy"; `migrate` should show
# "exited (0)" (it's a one-shot job, not a long-running service).

# API reachable, DB connection ok?
curl http://localhost:8000/health
# {"status":"ok","database":"ok","tracked_tickers":["SPX","NDX","VIX"]}
# status/database will say "degraded"/"unreachable" if the API can't
# reach the DB — check `docker compose logs timescaledb` if so.

# Ingestion actually resolving contracts and subscribing?
docker compose logs ingestion
# Look for "Subscribed to N new option contract(s)" shortly after
# startup. If it's empty, double check config.yaml's delta ranges aren't
# so narrow nothing qualifies, and that TASTYTRADE_* creds in .env are
# correct (auth failures log clearly rather than failing silently).

# Actual rows landing? (give it a couple minutes after startup first —
# bars only flush once their minute has fully elapsed)
curl http://localhost:8000/metadata
```

Interactive API docs (auto-generated by FastAPI) at http://localhost:8000/docs.

### Configuring tickers

Edit `config.yaml` — one entry per ticker you want tracked, with its own
delta range and expiration cap. See the comments in `config.yaml` and
`service/config/settings.py` (`TickerConfig`) for the full field list. One
thing worth knowing before you add a ticker: **`exclude_am_settled`
defaults to `true`, which is correct for most index/ETF options (SPX,
NDX, etc. — where AM vs PM settlement is a per-contract distinction) but
wrong for VIX specifically**, where *every* contract is AM-settled
(settlement is the VRO Special Opening Quotation, computed the morning of
expiration). Leaving the default on VIX silently tracks zero contracts
for it — set `exclude_am_settled: false` there, as `config.yaml` already
does.

Contract-refresh cadence (how often new listings/expirations get picked
up) is configured separately, via `.env`, since it's deployment tuning
rather than a per-ticker setting — see the `CONTRACT_REFRESH_*` block in
`.env.example` and the comments on those fields in
`service/config/settings.py` for the full rationale (short version: a
faster cadence automatically kicks in for a configurable window around
market open specifically to catch same-day/0DTE listings promptly).

## Using the query API

```bash
# 1-minute option bars for SPX calls with delta 0.15-0.85, over a date range
curl "http://localhost:8000/options/bars?ticker=SPX&start=2026-07-01T00:00:00Z&end=2026-07-02T00:00:00Z&right=call&min_delta=0.15&max_delta=0.85"

# Same, but 5-minute aggregated (from a continuous aggregate view instead of the raw table)
curl "http://localhost:8000/options/bars?ticker=SPX&start=2026-07-01T00:00:00Z&end=2026-07-02T00:00:00Z&agg=5m"

# A single contract's full history
curl "http://localhost:8000/options/bars?ticker=SPX&start=2026-07-01T00:00:00Z&end=2026-08-15T00:00:00Z&contract_id=.SPX260814C4500"

# Underlying bars - 1m or aggregated (5m/15m/30m/1h/1d/1w), same as options
curl "http://localhost:8000/underlying/bars?ticker=SPX&start=2026-07-01T00:00:00Z&end=2026-07-02T00:00:00Z"
curl "http://localhost:8000/underlying/bars?ticker=SPX&start=2026-07-01T00:00:00Z&end=2026-07-08T00:00:00Z&agg=1h"

# Which contracts are/were tracked for SPX, expiring in a given window
curl "http://localhost:8000/contracts?ticker=SPX&start=2026-07-01&end=2026-07-31"

# Quick summary of what data exists: tracked tickers, each one's date range, total row count
curl "http://localhost:8000/metadata"

# Find gaps in SPX's underlying bars over a range (max 120 days per request — see the endpoint's
# own docstring in service/api/routes.py for why), reporting missing-minute ranges during regular
# trading hours. Deliberately underlying-only, not option contracts — see
# service/ingestion/gap_detection.py's module docstring for why an option contract going quiet
# isn't the same kind of "gap".
curl "http://localhost:8000/gaps?ticker=SPX&start=2026-06-20T00:00:00Z&end=2026-08-06T00:00:00Z"
```

`/options/bars`, `/underlying/bars`, and `/contracts` paginate via `limit`/`offset` (default limit 1000,
max 20000) — check the response's `returned` field against `limit`: if they're equal, there may be more
data, page with `offset`. `/metadata` and `/gaps` are unpaginated — `/metadata` is a fixed-shape summary,
and `/gaps` returns one row per detected gap (typically far fewer than the bar count), not a filtered
list of bars.

If `API_KEY` is set in `.env`, every request needs a matching `X-API-Key` header (`/health` and `/` are
exempt).

## Finding and fixing gaps in underlying data

Two related but different things:
- **`GET /gaps`** (above) *reports* missing minutes — read-only, cheap enough to poll periodically
  (within its 120-day-per-request cap) to monitor coverage, but doesn't fix anything itself.
- **`docker compose run --rm gap-reconcile`** (or `python -m service.ingestion.backfill
  --reconcile-underlying-gaps`) actually *fills* them — scans each `capture_underlying_bars` ticker's
  full lookback window for missing minutes and re-requests candles starting from the earliest one found.
  Slower than a routine `backfill` run (it scans everything rather than just picking up where the last
  run left off), so it's meant to be run occasionally/on a schedule, not on every tick.

**There's no in-process scheduler for either of these** (that's Task 11 in `PLAN.md` — monitoring/
alerting, deliberately deferred as lowest-priority/optional). The recommended way to run
`gap-reconcile` regularly is host cron or a systemd timer, e.g.:
```
0 6 * * * cd /path/to/options-service && docker compose run --rm gap-reconcile
```

**Neither can recover data older than TastyTrade's ~6-week candle retention window** (Task 0's
confirmed finding) — a gap that old is real and will keep showing up in `/gaps`, but no amount of
backfilling brings back data the feed itself no longer has. `/gaps`'s own response doesn't try to guess
which of its reported gaps fall in this bucket; if a gap's `start` is much older than ~6 weeks ago,
that's the likely explanation for why reconciling doesn't clear it.

## Running tests

Unit tests (mocked — no TastyTrade credentials, no Docker needed):
```bash
pip install -r requirements-dev.txt
pytest
```

**One test file needs a real Postgres to actually run** (skipped by default, shown as `s` in pytest's
output): `tests/test_enum_serialization_postgres.py`, which exists specifically because of a real bug
(see PLAN.md Section 7) that was completely invisible to the rest of this SQLite-backed test suite —
SQLite has no native enum type, so it can't catch a mismatch between how SQLAlchemy serializes a Python
enum and how a real Postgres enum type actually validates it. To run it for real:
```bash
docker compose up -d timescaledb
TEST_DATABASE_URL=postgresql+asyncpg://<user>:<password>@localhost:$HOST_DB_PORT/<db> \
  pytest tests/test_enum_serialization_postgres.py
```
(use the same user/password/db/port as your `.env`)

**Smoke tests — via `docker compose run` (recommended, no local Python setup needed).** Every service
shares the same built image, so any smoke test can run by overriding the command on an existing
service — reusing its env vars (`.env`), network access (can reach `timescaledb` by service name), and
`config.yaml` mount, without shelling into a container or setting up a local venv:
```bash
docker compose build   # after pulling any code update, before the run commands below

docker compose run --rm ingestion python -m scripts.task2_smoke_test --ticker SPY
docker compose run --rm ingestion python -m scripts.task3_smoke_test
docker compose run --rm ingestion python -m scripts.task4_smoke_test
docker compose run --rm ingestion python -m scripts.task5_smoke_test --lookback-days 10
docker compose run --rm ingestion python -m scripts.task6_smoke_test
```
(`ingestion` is just a convenient existing service to borrow the environment from — `api` would work
identically. `task6_smoke_test` doesn't need TastyTrade credentials at all, pure DB reconciliation, so
it'll run fine even without `.env` fully filled in.)

The real backfill/reconciliation jobs have dedicated one-off services (profile-gated, so they don't run
as part of default `docker compose up`):
```bash
docker compose run --rm backfill                 # incremental by default — see "Backfill behavior" below
docker compose run --rm backfill --full          # force a full re-scan of the whole lookback window
docker compose run --rm greeks-backfill
docker compose run --rm gap-reconcile            # see "Finding and fixing gaps" above
```

**If you have a local Python environment set up instead** (venv with `requirements.txt` installed, and
`DATABASE_URL` pointing at `localhost:$HOST_DB_PORT` rather than the `timescaledb` service name), the
same scripts run directly:
```bash
python -m scripts.task2_smoke_test --ticker SPY
```

## Operating this deployment day to day

- **Backfill behavior:** `backfill` is incremental by default — each contract/underlying resumes from
  its own latest existing bar rather than re-requesting the full lookback window every run (this used to
  make every run take 15-30 minutes regardless of whether there was anything new; see PLAN.md Section 7
  for the bug writeup). Pass `--full` to force the old always-full-lookback behavior for an occasional
  deep re-verify. Neither mode looks for gaps *earlier* than a contract/ticker's latest bar — that's what
  `gap-reconcile` is for (see "Finding and fixing gaps" above).
- **Log volume:** if you're seeing (or saw, on an earlier version) an overwhelming amount of log output
  from `ingestion`/`backfill`, that was a real bug, not expected behavior — the `tastytrade` package sets
  its own internal logger to DEBUG on import, independent of this app's own logging config, and logs the
  full raw JSON of every single websocket message at that level. Fixed in `service/logging_config.py`
  (see its module docstring for the full root-cause writeup); every entry point now silences it properly.
  Set `LOG_LEVEL=DEBUG` in `.env` if you want more detail from *this app's own* code specifically — e.g.
  a per-bar line (contract, expiration, strike, delta, close) for every bar `ingestion` writes — without
  reintroducing the dependency's flood.
- **Restart policy:** `ingestion` and `api` both run `restart: unless-stopped` — they come back
  automatically after a crash or host reboot (as long as you didn't explicitly `docker compose stop`
  them). `timescaledb` is the same. `migrate`/`backfill`/`greeks-backfill`/`gap-reconcile` are one-shot
  jobs (`restart: "no"`) — they're supposed to exit, that's not a failure.
- **Healthchecks:** `timescaledb` and `api` both have real Docker healthchecks (`docker compose ps`
  shows their status) — `api`'s specifically calls its own `/health` endpoint and fails the check if the
  DB is unreachable, not just if the process is alive. `ingestion` deliberately has none: it has no HTTP
  surface to probe, and "is the process alive" is already covered by `restart: unless-stopped`. Real
  liveness monitoring (e.g. "no new bars in N minutes during market hours") is Task 11 in `PLAN.md`,
  explicitly deferred as lowest-priority/optional — in the meantime, `docker compose logs -f ingestion`
  or `/metadata`'s per-ticker time range is the way to check it's actually producing data, not just
  running.
- **Resource limits:** none are enforced by default (see the commented-out `mem_limit`/`cpus` lines next
  to each service in `docker-compose.yml`). Deliberate for a personal-project-scale deployment — a hard
  memory cap on `timescaledb` in particular risks turning a temporary spike (e.g. during a continuous
  aggregate refresh) into an OOM crash-loop instead of just slowing down. Uncomment and size those lines
  to your hardware if you're running this alongside other memory-sensitive services and want a ceiling.
- **Restarting after downtime:** once back up, run `docker compose run --rm backfill` then
  `docker compose run --rm greeks-backfill` to fill in whatever gap the outage left — both are
  idempotent (safe to run even if there's no gap).

docker compose exec timescaledb psql -U options_user -d options_data

## Running migrations without the full stack

If you're iterating on the schema and don't want to rebuild the image every
time:
```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL=postgresql+asyncpg://options_user:changeme@localhost:${HOST_DB_PORT:-5432}/options_data
alembic upgrade head
```
(Requires TimescaleDB to already be running and reachable on localhost —
e.g. via `docker compose up timescaledb`. If you changed `HOST_DB_PORT` in
`.env` because 5432 was already taken, use that same port here.)

## Repo layout

```
service/
  sources/     — MarketDataSource interface + TastyTradeSource (auth, chain lookup, streaming, candles)
  ingestion/   — ContractManager (contract resolution/refresh), IngestionPipeline + BarAggregator
                 (live streaming -> 1m bars), BackfillJob (historical candles, incremental by default,
                 plus underlying gap detection/reconciliation), gap_detection.py (missing-minute scanning)
  greeks/      — Black-Scholes calculator + GreeksBackfillJob (fills in Greeks for backfilled rows)
  api/         — FastAPI query app: /options/bars, /underlying/bars, /contracts, /metadata, /gaps, /health
  db/          — SQLAlchemy models, session management, continuous-aggregate view definitions
  config/      — config loading/validation (config.yaml + .env merged into one AppConfig)
  logging_config.py — shared logging setup; silences a real log-flood bug in the `tastytrade` dependency
alembic/       — DB migrations, including the Task 7 continuous aggregates
scripts/       — one-off utility scripts: task0_spike/ (TastyTrade credential setup + the candle-depth
                 feasibility spike) and taskN_smoke_test.py (real-credentials smoke tests per task)
docker-compose.yml
Dockerfile
PLAN.md        — the full project plan, rationale, and per-task implementation log; read this for detail
                 beyond what's summarized here
```
